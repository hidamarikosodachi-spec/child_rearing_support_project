# KGI・KPI と PDCA の設計 v1（note／Instagram／Threads・2026-11-15 オーナー指示）

> 目的：チャネルごとに「何を達成したいか（KGI）」「それを動かす毎週の指標（KPI）」「どう直すか（PDCA）」を固定し、**感覚でなく数字で次の一手を決める**。
> 期間：2026-11-16 〜 2027-02-14（13週）。事業判定は 12/26（[[business_plan_v1]]：web PV 月1,000 or フォロワー30）。

## 1. チャネルの役割（ファネル）

```
Threads / IG（見つけてもらう）→ note（読んで信頼する）→ サイト・診断（行動する）
```

- Threads・IG ＝ **到達**（知らない人に届く）。note ＝ **信頼**（読み込まれる）。診断 ＝ **転換**。
- いまの最大のボトルネックは**到達**（フォロワー：note 8／IG 1／Threads 1）。

## 3. KPI ツリー（毎週金曜に見る）

先行指標（自分で動かせる）→ 結果指標（KGI に近い）の順。

### note
- 先行：公開本数（週7）／見出し画像の型／タイトルの型
- 中間：インプレッション/日（基準 約58）／**PV÷インプレッション**（クリック率の代用）
- 結果：週間 PV／スキ率（スキ÷PV）／フォロワー増／診断への遷移

### Instagram
- 先行：投稿数（カルーセル週5・リール週2）／表紙の型（CC 実験）
- 中間：**リール＝平均視聴時間 ≥6秒**／**カルーセル＝保存÷リーチ**／リーチ/本
- 結果：リール再生数／フォロワー増／プロフィールアクセス

### Threads
- 先行：投稿数（毎日）／1行目の型・末尾の問い（TH-2）
- 中間：**投稿後1時間の返信数**／閲覧数の中央値（基準 54）
- 結果：1投稿の最大 views／フォロワー増／プロフィール閲覧

## 4. PDCA ループ

| 周期 | 内容 | 担当 | 成果物 |
|---|---|---|---|
| 毎日 | **Do**：投稿・コメント返信。投稿に「実験ID」と「仮説」を付ける | CEO | 台帳（posting_schedule） |
| 毎週金曜 | **Check**：`insights_all.py` ＋ `ig_reel_insights.py` ＋ `note_dashboard.py` を回し、KPI 表を更新 | CEO | [[pdca_log]] に1行/チャネル |
| 毎週金曜 | **Act**：下の判定ルールで継続・修正・停止を決め、翌週の仮説を1つ置く | CEO | this_week.md |
| 毎月末 | KGI の進捗確認と、目標値の見直し | CEO＋オーナー | 月次レビュー |
| 12/26 | 事業判定（web 集客を続けるか） | オーナー決裁 | 判定メモ |

### 判定ルール（実験を回す共通ルール）
1. **1回に変えるのは1変数**（型・題名・時間帯のどれか1つ）。
2. **最低3本**で比べる。1本の当たり・外れで判断しない。
3. 比べる指標は、その媒体の**中間 KPI**（上の太字）。
4. 基準（直近同媒体の中央値）に対して、**+30% 以上＝採用**／**−30% 以下＝停止**／その間＝**あと3本延長**。
5. 判定は投稿**7日後**（IG の速報は48時間後）。
6. **事実を盛って数字を取りに行かない**（研究の限界は必ず書く）。安全柵（BAN リスク・売り込み禁止・医療断定禁止）は実験の対象外。

## 5. 計測の穴（先に直す）
- **IG のフォロワー数とカルーセルのリーチ・保存**は、`insights_all.py` に入っていない（IG は手入力 2026-09-29 のまま）。→ 次の作業で自動取得に追加する。
- note の「PV÷インプレッション」は、日次インプレッションと記事別 PV の突き合わせが必要（週次で手計算）。
- Threads の「投稿後1時間の返信」は、投稿直後の取得が要る（毎日 13:00 に1回取る運用にする）。
